
## Code Review — PR #33: composer append pipeline, Drive delete/restore, taxonomy

**Verdict: APPROVE.** No blocking defects. The Google Docs index arithmetic underlying the append-with-tables pipeline is correct and internally consistent; the Drive delete/restore gating is sound; the taxonomy changes are benign. Two non-blocking observations noted at the end.

**Scope:** read the full diff and all 16 commit messages, then verified the implementation directly in `google_docs_client.ex`, `documents.ex`, `taxonomy.ex`, and the new append test file — not the commit narratives. Where a commit asserted an invariant (descending request order, UTF-16 indices, lost-gating, table cross-section matching), I read the code to confirm or refute it, and checked the Google Docs API `GlyphType` semantics against the authoritative reference.

### Verified clean

The hardest parts of this PR are the Docs-API index mechanics in the append pipeline, and they hold up under direct read:

- **Descending `createParagraphBullets`.** `paragraph_bullet_requests/2` builds its contiguous groups in ascending offset order and emits them through `Enum.reverse()` (`google_docs_client.ex:2565`), so the `createParagraphBullets` requests apply highest-index-first. This is necessary: `createParagraphBullets` strips leading tabs, shifting later indices, and emitting descending means each create only touches paragraphs at higher indices than the remaining creates. Within the assembled batch (`append_template/3`, `:1767`), the `createParagraphBullets` group is the *last* style pass and the only one that shifts indices — `updateTextStyle`, `updateParagraphStyle`, and the preceding `deleteParagraphBullets` all leave indices untouched — so it cannot disturb earlier style targets either.
- **Stray-bullet clearing on the first appended paragraph.** `clear_inherited_bullets/2` (`:2580`) emits one `deleteParagraphBullets` over `[content_start, content_start + utf16_units(text)]`, covering the whole inserted body. Because `insertPageBreak` is an *inline* element (not a paragraph break), `content_start` (`insert_index + 2`) lands *inside* the first appended paragraph, so the delete range overlaps that paragraph and clears any bullet it inherited from the target's preceding list-item paragraph — the exact stray-glyph case the forced `"\n"` split was added to prevent.
- **UTF-16 index math.** `utf16_units/1` (`:914`) transcodes UTF-8→UTF-16 and halves the byte count, correctly counting surrogate pairs as two units, matching Google Docs' index semantics. Every offset (`start_offset`, `endIndex`, marker ranges, style-run spans) flows through it.
- **Drive delete/restore lost-gating.** `move_to_deleted_folder/3` (`documents.ex:1786`) soft-deletes on a `:drive_file_not_found` only when `file_marked_lost?/2` confirms the row's status is already `"lost"`; a `:move_failed` (and any other error) fails the delete. The distinction is genuine: `do_move_file/2` (`google_docs_client.ex:1398`) GETs the file's parents first, so a 404 there means the file is gone (`:drive_file_not_found`, `:1431`), whereas a 404 on the subsequent PATCH means the *destination folder* is gone (`:move_failed`, `:1420`). The `"lost"` gate is the right defense against Drive returning 404 (not 403) for a live-but-unreadable file — an independent sync pass must have already confirmed the file is gone before the row is trashed.
- **Table cross-section matching, column-width replay, ragged-row padding, empty-cell paragraph replay** — read and consistent with the commit claims (block-level `startIndex` reads, Phase-2 width replay after re-fetch, per-row normalization to the declared column count, paragraph-style replay on empty cells).

### Bullet-glyph allowlist is correct

`resolve_bullet_preset/3` (`google_docs_client.ex:2241`) classifies a list level as numbered when its `glyphType` is in `~w(DECIMAL ZERO_DECIMAL UPPER_ALPHA ALPHA UPPER_ROMAN ROMAN)`, otherwise bullet (`BULLET_DISC_CIRCLE_SQUARE`). I checked this against the Google Docs API `GlyphType` enum, and those six are *exactly* the ordered glyph types the API defines. Note specifically that the API's lowercase-letter glyph is named `ALPHA` (a, b, c) and its lowercase-Roman glyph is named `ROMAN` (i, ii, iii) — there is **no** separate `LOWER_ALPHA`/`LOWER_ROMAN` value (those names belong to CSS/OOXML, not this API). Both are already in the allowlist, so a standard multi-level numbered list (1 → a → i) resolves all three levels to `NUMBERED_DECIMAL_ALPHA_ROMAN`. The catch-all only ever receives `GLYPH_TYPE_UNSPECIFIED`/`NONE` (sentinels) or unordered levels — and unordered levels carry `glyphSymbol` rather than `glyphType`, so the `%{"glyphType" => _}` pattern does not match them and they correctly fall through to bullet. No gap. (The remaining approximation — that only glyph *family* is reproduced, not exact custom glyphs — is an inherent limitation of `createParagraphBullets`' fixed preset enum, documented in commit 55cb044.)

### Observations (non-blocking)

- **Append tests are mock-driven and self-consistent, not API-validating.** Every flow test injects `:get_fn`/`:batch_fn` stubs that encode the same Docs-API model the implementation assumes (that `insertTable` shifts the resulting `startIndex` by +1, that a bare cell carries a trailing `"\n"` at `insert_index+1`, that pre-existing tables surface `startIndex` on the structural block). If any of those model assumptions were wrong against the live API, the stubs would still return exactly what the code expects and the suite would stay green. This is the known limit of mocking a third-party API — and it has bitten here before (the nested-`table`/`startIndex` bug, where the original stubs mirrored the bug rather than the real shape). The real validation weight therefore rests on the per-commit "verified live" claims, not the ~3300 test lines. Not a defect; worth keeping in mind when calibrating confidence.
- **`phoenix_kit` requirement widened to `>= 1.7.189 and < 3.0.0`** (`mix.exs:77`). Deliberate and documented — the module's contract surface (`PhoenixKit.Module`, Settings, Integrations, etc.) is stable across the announced 1.8/2.x lines. The cap guards only against a 3.0 break, so an as-yet-unreleased 2.x with a silent contract change would resolve cleanly and fail at runtime. Acceptable for a Hex-published module asserting contract stability; a CI run against core's tip before each `2.x` lands upstream would close the residual gap.

**Verdict: APPROVE.** The core corruption fixes — index arithmetic, UTF-16, table matching, delete/restore gating — are correct under direct verification; the bullet-glyph allowlist matches the API enum exactly; the observations above are non-blocking.
